# MMHotline acceptance contracts

These contracts describe the current one-server workflows and their required
outcomes. The [validation record](validation.md) distinguishes automated
checks, browser checks, and external delivery that has not been verified.

The baseline is one installation with one team, human responders, shared
contact methods, and a primary/backup schedule. The team's settings come from
one [settings file](design/settings-file.md); setup creates one
`mmhotline.db` database containing the team name and all application state
([storage](design/operation.md#storage)). An SOS is the urgent alert that
wakes the person on call, even at night; claiming an incident tells the team
you are handling it, and MMHotline stops contacting the next person.

| ID | Supported workflow | Required outcome | Owning design |
| --- | --- | --- | --- |
| A01 | Sign in and manage people | Setup creates one team and no person. The settings file's `people` part adds, changes, and deactivates people, matched by sign-in email address. The settings file lists at least one administrator. A sign-in email address identifies active members, taken from a verified Cloudflare Access token or a one-time sign-in link. The root command `people create-sign-in-link` creates the link. Without Cloudflare Access configured, the 401 page shows sign-in link instructions unfolded and offers no Access link. Missing or invalid identity gets 401, unknown identity gets 403, and Cloudflare Access keys that cannot be fetched get 503. Recheck active membership and required roles inside the database transaction for each application operation. The People page and `people list` show the people read-only. Callers authenticated as root through the command Unix socket have no member ID and can edit personal contact methods. Refuse deactivation while the person owns a claimed incident or has temporarily taken on-call duties instead of following the schedule. A refused deactivation rejects every addition, change, and deactivation in the `people` part, keeping the previously applied people. Deactivation cancels the person's queued deliveries and ends the person's sign-in links, and names stay in history. Keep CSRF protection. | [People](design/people.md), [settings file](design/settings-file.md#people) |
| A02 | Receive an alert | Authenticate the sending alert source. Validate and normalize the alert payload using the [intake field and request rules](design/ingestion.md#alert-intake). Commit the accepted alert before reporting success, and return the MMHotline alert ID. Missing severity becomes warn with an explanatory normalization note. Rejected input creates no accepted alert. A repeated `sender_alert_id` from the same alert source with the same severity, title, message, and `sender_incident_key` is one alert, answered `already_received: true`. A different alert that reuses the `sender_alert_id` is refused with a signed `400`, "sender_alert_id already used for a different alert". A resolution closes the matching unresolved incident. `sender_incident_key` matches an unresolved SOS incident (open or claimed) from the same alert source. A new SOS that joins a claimed incident goes once to the person who claimed the incident, through that person's contact methods subscribed to SOS, waking ones included, and the incident history records it. Signed requests use `/alert-intake/{alert_source_id}` on the address set by `alert_intake_listen_address`, never the pages' address set by `web_listen_address`. Responses return `mmhotline_alert_id`, optional `mmhotline_incident_id`, and `already_received`. Intake limits refuse a flood of Warning and Info alerts with `429`. Never refuse an SOS for rate. An alert source with 250 pending SOS deliveries gets `429` for a new SOS, so one alert source's flood of SOS deliveries leaves room in the delivery queue for another alert source's SOS; the limit on open SOS incidents applies to all alert sources together. Due SOS deliveries go out from the alert source with the fewest due first, so a flood never puts another alert source's SOS behind its backlog. A correctly signed SOS refused for any reason opens one MMHotline SOS incident for the alert source. That incident and its deliveries persist even when the pending deliveries are full. | [Ingestion](design/ingestion.md) |
| A03 | Route an ordinary notification | Match subscriptions by base severity: info, warn, or sos, including each base severity's resolved variant. Honor unavailability, `send_while_unavailable_or_muted`, and team mute, including for shared contact methods. Team mute always suppresses Pushover messages and phone calls. Never call for resolved-sos, the alert reporting an SOS incident's resolution. Send a resolved-sos message only to a contact method that MMHotline attempted to send an SOS or a warning about the incident (the SOS itself, an escalation, or a warning on the incident): a resolved message tells the end of something the person was told about, so a contact method that got nothing gets no resolved message, and a held SOS the triage agent fixed sends none to Pushover while email, which got the SOS at once, gets it. For contact method types except webhook, combine Warning, Info, and resolved messages per contact method without dropping alert records. SOS bypasses the ordinary throttle. Slack and Telegram have a separate SOS flood rule. Show delivery outcomes separately from incident state. Saved contact methods are ready to receive alerts immediately. Creating a contact method or changing a destination queues one test in the save transaction. The test names who created or changed the contact method. Subscription-only changes queue no test. Send test keeps the minute and phone call limits. Each contact method's card on the Contact methods page shows the contact method's latest test outcome. | [Notifications](design/notifications.md) |
| A04 | Handle an SOS | Open an incident and notify the eligible on-call responder. Any signed-in member, including an administrator, may claim, reassign, escalate, or resolve the incident. Retain the ordered action history. Claiming stops SOS repeats, and escalation transfers responsibility. On the incident page, a claim or a resolve takes an optional note: one line, trimmed, at most 500 characters, without control characters. Refuse a longer note or a note with a control character, give the reason, and change nothing. The claim or resolve history entry keeps the note. `incidents show` displays the note after the entry's own text as `Note from NAME: “NOTE”`, and includes the JSON field `note`. The incident page shows the note on the history entry's line with the writer's name, or `Your note: “NOTE”` to the writer. The incident page names whom MMHotline wakes and counts down to the incident's next automatic step. While the SOS waits, offer Claim, Resolve, and Escalate. Once claimed, offer Take over to anyone but the owner, and offer Resolve and Escalate. Claim and Resolve submit the incident page's single note field. Once resolved, offer no incident action. The What happened list is oldest first. Fold rounds that wake the same people again into one line with a count, and end the list with the next step. Show no internal value such as a step name or a delivery's internal reason ([the incident page](design/incidents.md#the-incident-page)). Claims and resolves from Pushover, Slack, Telegram, and calls cannot include a note. `mmhotline incidents send-test-sos` opens a test SOS from MMHotline itself, titled `Test of the alerts. Nothing is wrong: acknowledge this.`, with the reserved alert source ID `mmhotline_test_sos`. It pages the person on call as a real SOS does, with the same contact methods, repeats, and backup timing, and skips the triage agent: it neither waits for the agent nor starts a triage session. A claim by any means resolves only a test incident at once, with the history line `Resolved by MMHotline after the claim, because this incident was a test`, and queues no message that the test is resolved. The command waits for the claim up to `--wait-for-claim-minutes` (default 10, at least 1), prints who claimed, how, and when, and exits 0; with no claim it exits 1, leaves the incident open, and names the Pushover app and critical alerts as what to check first. A new test first resolves an unclaimed earlier test. With `--sign-in-email-address ADDRESS`, the test goes only to that person's contact methods now, whether or not they are on call: it opens as a chosen-person SOS without a time to claim, never goes on to a backup or anyone else (also when that person becomes unavailable), repeats to them until they claim it, and then resolves as above. A person who is not on the team, is unavailable now, or has no contact method that wakes people for SOS alerts is refused, and nothing opens. Without the flag, a team of exactly one person is tested as if that person's address were given. The result and JSON name the person (`sent_only_to_name`, `sent_only_to_sign_in_email_address`). | [Incidents](design/incidents.md) |
| A05 | Escalate an unanswered SOS | Contact the primary, then the backup, then everyone available, with visible times for the next step. Each step before everyone available waits the time to claim: five minutes, or whole minutes from 1 to 60 set by `on_call_schedule.escalate_if_unclaimed_after_minutes` in the settings file. A changed time to claim reaches steps starting after the change, while a step under way keeps the recorded end time. With the triage agent, the first step may wait up to 15 minutes (A19). Skip unavailable recipients. A one-person team retries the person. No new call overlaps a known active call to the same recipient, including after restart. Poll known Twilio calls at least five seconds apart until a final status or three minutes after creation. Unchanged polls and idle installations write nothing. Calls direct people to Pushover or MMHotline to claim. After the fallback, contact the eligible team until someone claims or resolves. With nobody eligible, contact every member. Explicit team mute still suppresses disruptive delivery. A person with no waking contact method is left out of the round, and the history says "Could not wake NAME: NAME has no contact method that wakes people for SOS alerts" once per step. When nobody in a step can be woken, the next step starts at once. The administrators get one warning notice per incident. Every open incident repeats and escalates, including one past the 1,000th. An incident whose handling fails is reported in the server log, and the other incidents still escalate. A due delivery that cannot be checked fails with the reason, and later deliveries still go out. | [Incidents](design/incidents.md) |
| A06 | Configure and inspect a schedule | Support By day of the week, By hour of the day, Weekly rotation, and Custom schedule. The settings file's `on_call_schedule` contains only the selected schedule type's keys and the time to claim. Validate the schedule with the schedule type's own rules, then preview with `schedules preview --settings-file`. Activate custom code only after successfully calculating assignments for the next 14 days and passing test cases. A refused schedule keeps the active schedule unchanged. Saving the selected schedule type removes the saved configurations of every other schedule type. Interpret shifts in the schedule timezone and display local conversions on the read-only On call page. | [Scheduling](design/scheduling.md) |
| A07 | Manage availability and taking on-call | Unavailability and taking on-call start immediately and expire after the duration chosen by the person applying the control. Team mute is an administrator-controlled team setting. Starting or ending team mute preserves each person's unavailability and contact-method preferences. Require explicit replacement of whoever took on-call. Reject concurrent stale changes. Never silently transfer claimed incidents. Explain effective coverage and suppression. | [Availability](design/availability.md) |
| A08 | Alert when check-ins stop | Accept signed check-ins from a sender expected to send every 30 seconds, and start expecting check-ins when the first check-in arrives. Measure the alert source's Warning and SOS thresholds from when MMHotline last heard from the alert source. At each threshold, alert through the normal ingestion and routing path. Planned downtime for check-ins, set by hand or taken from a maintenance window listed by the sender, always has an end. During planned downtime, record check-ins and make no alerts about missing check-ins. Show the source’s check-in status before setup facts and reuse the status on the alert sources list. Display check-in and downtime times, and interpret the downtime form’s end time, in the team’s time zone. When check-ins resume, resolve an unclaimed SOS incident automatically and leave a claimed one open for the person who claimed it. A source already marked stopped keeps the recorded times across restart. A recently heard source starts counting silence at the first database read after restart, because recent arrival times existed only in memory. | [Monitoring](design/monitoring.md) |
| A09 | Extend the product | Keep the team’s logic on the team’s systems through its monitoring tools, outgoing webhook contact methods, and inbound signed generic alerts. MMHotline runs two kinds of team program in sandboxes: custom schedule code in a locked-down Starlark sandbox with limits, and the triage agent in its separate systemd sandbox; built-in alert source types are written in Go by MMHotline. MMHotline also runs the `mmx` program (A18). For the dashboard, MMHotline also asks systemd to run the one command root sets in the settings file's `fleet_view_command` (A24). | [Scheduling](design/scheduling.md#custom-schedule-code) |
| A10 | Survive interruption and inspect failures | Persist accepted alerts, incident transitions, and notification intent before reporting success. Resume current eligible work without replaying missed notification repeats, escalation windows, or schedule handoffs. Preserve ordinary pending deliveries, identify uncertain delivery, and prevent stale jobs from reopening or escalating a resolved incident. Sending service delivery rules follow [notifications](design/notifications.md). Retry limits and delivery outcomes remain explicit. A panic in one round of a background loop is reported with its stack, like a returned error, and the loop goes on. The installed units restart MMHotline and the backup with no start limit. Database retention is not automated. | [Operation](design/operation.md) |
| A11 | Find and act on an incident | Show unresolved SOS incidents on the dashboard. List every unclaimed incident under Needs a person, oldest first, with no limit, with whom MMHotline wakes now, a countdown to the next automatic escalation step, and Claim. List claimed incidents under Being handled with who claimed each incident and no Claim. Needs a person also lists refused commits awaiting review, approval requests awaiting a person's permission to run a playbook, and warned runs scheduled to run unless someone presses Stop. Show All clear when no unclaimed or claimed SOS incident, approval request, refused commit awaiting review, or warned run remains in the dashboard's lists. Provide searchable history on Alerts, with severity, full titles, receipt times, and named incident outcomes in a wrapping list. Alert times and receipt-date filters use the team’s time zone. Show current primary and backup on the dashboard, and accessible actions and audit details on incident pages. Update visible state after another user acts. Browser errors and unknown paths keep their HTTP status and show a readable reason and a recovery link in the page frame. Preserve non-page error responses and rate-limit retry headers. | [Interface](design/interface.md) |
| A12 | Build and run the application | Build Go binaries with cgo disabled. Setup creates one team from the settings file's `team_name`. Serve the pages on the settings file's web listen address for the Cloudflare tunnel and SSH forwards. Serve only signed intake on the private-network alert intake address. Serve the private command Unix socket with checked peer credentials. Configure sending services and contact methods through shared operations, with text or JSON command results and atomic secret files. Shut down cleanly. | [Development](design/development.md) |
| A13 | Install, upgrade, and optionally back up | Before any change, root installation on Linux with systemd checks `/etc/mmhotline/mmhotline_settings.yml`. Refuse a missing file or a failed owner/mode or static check. The refusal names `/etc/mmhotline/mmhotline_settings.yml` and the installation instructions in [Install MMHotline](../how-to/install.md). The root installation operation then installs the binary and creates missing state, with the settings file's `team_name`. Installation sets the settings file's group to `mmhotline` and mode to 0640. Installation installs the service that reads the settings file, with the [systemd service restrictions](design/operation.md#installation-and-setup). Installation also installs the fleet view's socket units, whether or not the settings file has `fleet_view_command`. Preserve existing state and never change the settings file's contents. An upgrade keeps the database and every row: opening `mmhotline.db` runs each [database format](design/operation.md#database-format-and-upgrades) upgrade step it has not had, once and in order, and refuses, changing nothing, a database without a format number or of a newer format than the program knows. An unchanged rerun makes no changes; upgrades restart the service and readiness is checked within 30 seconds. Start the separate Litestream service, `mmhotline-backup.service`, only when backup settings and the Litestream program exist. Application processes never receive backup credentials: Litestream runs as its own Unix user, `mmhotline-backup`, with group `mmhotline`, so `mmhotline serve` cannot read the credentials from Litestream's process. The state directory has mode 0770 and the database files mode 0660, so Litestream can write the database. Litestream keeps its working files in `/var/lib/mmhotline-backup/mmhotline.db-litestream`, set in the generated `/etc/mmhotline/litestream.yml`, in a mode-0700 directory that systemd creates for `mmhotline-backup`; neither an upgrade nor a restore needs a change of their owner. Installation changes each file's owner and mode through the opened file and refuses a symbolic link. `sudo mmhotline backup check-uploads` is a read-only local command. Exit 1 when Litestream has not captured the database's newest change within 30 seconds: the newest committed transaction in the write-ahead log, compared with the newest captured change's LTX header, or, with an empty log, the database file's last write. Exit 0 when Litestream captured the database's changes and the backup holds every captured change, or every missing change was captured less than 5 minutes ago. Exit 3 before Litestream has captured any changes. Exit 1 when the backup lacks a change captured more than 5 minutes ago. Name the newest captured transaction and the newest uploaded transaction. Exit 3 when the check cannot tell: backup not configured, Litestream missing, `litestream ltx REPLICA_URL` failing, or no `max_txid` column. `mmhotline backup check-uploads` reads the `litestream ltx REPLICA_URL` output's `max_txid` column by name. The backup check passes `backup.env`'s variables only to `litestream` and never prints a credential. Document restoring with `mmhotline.service` and `mmhotline-backup.service` stopped, old state and Litestream's old working files preserved, and restored files owned by the service user, with mode 0770 for the state directory and 0660 for the database. Document [startup recovery of current eligible work](design/operation.md#recover-current-work). Backup is optional; unuploaded changes can be lost and a tried restore is encouraged. | [Operation](design/operation.md#setup-backup-and-restore) |
| A14 | Recover after a server restart | Accepted alerts and eligible delivery intent survive a restart. Queued notifications still required under current membership, availability, contact methods, mute, and incident state may repeat but are not skipped. Sources heard recently get their full Warning and SOS times from the first read of the database after restart. Sources already marked stopped (`check_ins_stopped`) keep their recorded times. | [Operation](design/operation.md#recover-current-work), [Monitoring](design/monitoring.md) |

Refuse a service's section left out of the file while contact methods use the sending service, naming their count and how to remove them; refuse a different Telegram bot while Telegram message contact methods exist, but accept a new token for the same bot. Accept a new Pushover application token while Pushover contact methods exist and keep them, refusing replacement only while an emergency receipt is open. SMTP setup checks connection, required TLS, and optional authentication without sending; credentials are paired and addresses plain ASCII. Setup alone sends no test; adding an email address, connecting the chat, or saving a personal Pushover key creates a contact method and queues its test. A Pushover test is an ordinary-priority notification titled `MMHotline can reach this phone`: it needs no acknowledgement and `Last test message: accepted` means only that Pushover took it. Each person's Pushover contact method shows whether an emergency test is acknowledged, in `contact-methods list` (text and JSON `pushover_emergency_test`) and on the Contact methods page: `Emergency test: acknowledged at TIME.`, or `Emergency test: not yet acknowledged. Run ...send-test-sos --sign-in-email-address ADDRESS...`, without `--sign-in-email-address` in a team of one person. RUN: ...` on its own line with a blank line around it, until proved. Pushover checks and stores the monthly message limit; person plus Pushover contact creation is atomic. Poll receipts no faster than every five seconds. Acknowledgement claims the incidents counted by the emergency message for the contact method's owner, without taking over another person's claim. | A17 | Decide which playbooks run without a person | After accepting and pushing the agent's commits, MMHotline runs `mmx explain` in MMHotline's systems-repository copy at its checkout, the trusted commit of A18, which is the pushed commit unless a commit waits for review. Read kinds from the explanation, never the playbook's name or the agent's words. Classify unknown modules, undecidable `when` conditions, disallowed arguments, and values needed for recognition but known only during execution as unrecognized tasks. The answer names at most 10 unrecognized tasks, giving each task's first broken recognition rule in plain words. For a failed recognition condition, use the condition's plain-language rule text as the reason. Also classify every `save_on_controller_machine` entry from `mmx explain` as an unrecognized task, listing controller-file entries before node tasks. Include entries from every fleet stage, including stages selecting no servers. Each entry's reason names the files written on MMHotline's server or says MMX knows the files only during execution. Read `mmx explain` schema_version 2 from MMX 0.1.0 onward. Refuse version 1, which omits the files saved on MMHotline's server, with a message to upgrade MMX. A playbook takes the strictest rule among the playbook's kinds on the inventory, unless the settings file lists the playbook by name. An inventory's optional `playbooks` lists ordinary playbooks, each NAME of `playbooks/NAME.yml`, with a rule checked as a kind's rule; a one-time playbook cannot be listed, and `settings check` names each problem's key path. ### Completion and review bar

Feature completion requires the agreed design to be implemented and the
feature's focused tests and matching [public workflows](testing.md#contract-map)
to pass.
Public workflows exercise the built interfaces listed in the contract map:
commands, browser actions, or alert API requests. The feature's documentation
must be accurate, including the design, how-to guides, command reference, and
acceptance contracts named in the
[documentation map](documentation-map.md#when-a-fact-changes). The feature's
row in the [Status table](design/README.md#status) must be updated with
[validation evidence](validation.md). A test double, local build, or sending
service request acceptance is not evidence of a real phone call or
end-to-end deployment.

A correctness blocker is a concrete violation of a contract in the supported
workflow or agreed operating envelope. Reproduce the contract violation. Keep
optional polish and new product requirements separate. Review the supported
workflows against the acceptance contracts in `docs/changing-mmhotline/acceptance.md`.
