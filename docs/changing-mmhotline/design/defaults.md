# First-build defaults for review

These defaults describe the current build. The linked specification owns each
complete behavior and its reason. `docs/changing-mmhotline/design/defaults.md` is a short index.
An SOS is the urgent alert that wakes the person on call, even at night;
to claim an incident is to say "I'm on it", which stops MMHotline
contacting the next person.

A value a reasonable team would choose differently is a setting, written out
with its default and the reason for the default. A fixed value records why it
is fixed. "No team has needed another value" is not such a reason: the
product has had few outside teams yet. A setting's allowed range needs its own
reason, such as a time below which a restart would wake someone.

| Choice | Starting default | Owner and reason |
| --- | --- | --- |
| `connect-pushover` questions | One person in `people` is chosen without a question; an unknown sign-in email address or device name is asked again; Enter at the device question means all devices | [Notifications](notifications.md#connecting-pushover-in-one-command): the token is already saved when the questions come, so a typing mistake should not mean pasting it again. |
| Settings page hierarchy | Setup status and next action first; one folded settings path per page; technical detail folded | [Interface](interface.md#settings-pages): routine checks need status and next actions, while repeated paths and technical output crowd a phone. |
| Browser error presentation | Frame browser navigation errors and unknown paths; preserve status codes, rate-limit retry headers, and non-page responses | [Interface](interface.md#shared-behavior): a person needs a readable reason and a way back, while senders and background fetches depend on their existing responses. |
| Triage session page hierarchy | State and Stop first, reports and alerts next; run steps, past runs, and session details folded; team-zone times throughout | [Triage session page](triage-agent.md#the-triage-sessions-page): the current work and findings matter before commands and background records, especially on a phone. |
| Triage agent internet access | `listed_hosts_only` until MMHotline applies the settings file. The file must supply `triage_agent.internet_access` | [Triage agent](triage-agent.md#internet-access): a new setup reaches only explicitly listed destinations. The settings file can select `any_site` when broader access is needed. |
| An SOS joining a session that already woke someone | No wait and no wake when every person the SOS would wake first had a waking message accepted for an unresolved incident of the open session; the time to claim then runs as usual | [Triage agent](triage-agent.md#an-sos-waits-for-the-agent): the person is already at work on the session. Only an accepted message counts, and an unclaimed SOS still escalates, because a rare second wake is better than a dropped SOS. |
| Triage agent run ceiling | One hour | [Triage agent](triage-agent.md#one-systemd-service-instance-per-run): systemd ends a hung run so the run cannot hold a triage session forever. |
| Triage agent setup test | Five minutes | [Triage agent](triage-agent.md#triage-agent-setup): the test asks for one sentence. A hung test must release the active run so a person can retry. |
| Triage agent open tunnels | At most 64 for each run, including connections still sending proxy headers. Separately, at most 64 connections may be waiting to identify a run | [Triage agent](triage-agent.md#every-connection-goes-through-mmhotlines-logging-proxy): bound memory and file descriptors used by a misled agent. |
| Triage agent report notification summary | At most 300 characters, shortened when necessary | [Triage agent](triage-agent.md#reports-to-people): about what a phone lock screen shows. The page keeps the report and evidence. |
| Triage agent step text | At most 2,000 characters | [Triage agent](triage-agent.md#the-connection-to-each-coding-agent): the page shows a summary. Coding agent session files retain the transcript. |
| Triage agent page and command | The Triage agent setup page and `triage-agent show` are for administrators. Local commands use trusted root access | [Triage agent](triage-agent.md#triage-agent-setup): the setup holds the credential used to sign in to the coding agent's service. |
| Rules for running the agent's playbooks: a kind without a saved rule, and an inventory the settings file leaves out | Without saved rules, every action kind uses “Get permission, then act” with 1 approval, including the “Check only” kind. If the settings file omits an inventory, MMHotline saves the approval requirement for every action kind. MMHotline marks application of the `rules_for_running_agent_playbooks` part as failed, naming the omitted inventory | [Settings file](settings-file.md#rules-for-running-the-agents-playbooks): a missing setting must never let a fix run without a person. No inventory gets a silent default. |
| A kind of action an inventory's `action_kinds` leaves out | “Get permission, then act” with 1 approval. The omitted kind appears as a note in `settings check`, `settings apply`, `settings show`, the page of rules for running the agent's playbooks, and `agent-playbook-rules show`. The note does not fail checking or applying the file | [Settings file](settings-file.md#rules-for-running-the-agents-playbooks): a later MMHotline may add a new action kind, so an existing settings file must still apply. The omitted kind uses the safest setting, “Get permission, then act” with 1 approval, and MMHotline shows the omission. |
| A playbook listed by name and the services list | A playbook listed under an inventory's `playbooks` keeps its listed rule even when a task acts on a service whose changes a person must approve | [Triage agent](triage-agent.md#playbooks-listed-by-name): the person listed the playbook knowingly, `every_server` restarts listed services as a matter of course, and the list keeps guarding the agent's one-time playbooks, which can never be listed. |
| Free disk space floors without a person | A journal vacuum keeps at least 1 day and 100 MiB; an image removal removes only images with no name left | [Triage agent](triage-agent.md#the-kinds-of-action): the journal is an incident's evidence, and 100 MiB holds about a day of a busy server's logs; a named unused image can be the only copy of a rollback. Any other value is an unrecognized task, which a person can approve. |
| Files shown with a playbook | The text of each copied file up to 16 KiB, all files up to 64 KiB, at most 50 files named; others by size and SHA-256 | [Triage agent](triage-agent.md#the-files-a-playbook-copies): a unit or configuration file fits many times over, and the bound leaves room for the playbook in the 256 KiB review prompt and kept text. A file is never cut, because a person would approve a part nobody showed. |
| API-key sign-in check | The vendor's models list, ended after 30 seconds; other credential types run the setup test's prompt, ended after 5 minutes | [Triage agent](triage-agent.md#the-daily-sign-in-check): the models list proves an API key at no cost and answers within about a second; the 30 seconds allow a slow network and still free the one triage run soon. |
| Coding agent model and reasoning effort | No default: `model` and `reasoning_effort` are required in each agent's section. MMHotline checks only the values' shape, and the setup test proves the values | [Settings file](settings-file.md#model-and-reasoning-effort): the values belong to the vendors and change every few weeks, so MMHotline names no model. |
| Services whose changes a person must approve | One installation-wide list applies to all inventories, from the settings file's `services_whose_changes_a_person_must_approve`, which may be `[]`. The page of rules for running the agent's playbooks shows the list | [Triage agent](triage-agent.md#services-whose-changes-a-person-must-approve): only the team knows which services must never start or stop without a person, so a setup can list the services. A team can instead instruct the agent through the systems repository's triage rules, so a list is not required. |
| `mmx explain` and `mmx nodes` time limit | Two minutes | [Triage agent](triage-agent.md#reading-a-playbooks-node-tasks): `mmx explain` and `mmx nodes` read files and take seconds. A hung command must not hold the one triage run. |
| `mmx explain` and `mmx nodes` output | MMHotline reads at most 64 MiB of output and 64 KiB of error output. Output over the limit is refused, never cut | [Triage agent](triage-agent.md#reading-a-playbooks-node-tasks): the agent controls the output's size through the playbook it commits, and MMHotline also delivers SOS alerts, so the output must not fill its memory. `mmx explain` of the largest playbook in a reference four-server setup prints 3.1 MiB for 4 servers, so 64 MiB fits about 80 servers. 64 MiB is also the fleet view's read limit. MMHotline judges a playbook, and keeps the output for the people who approve, only as a whole. |
| Playbook file that MMHotline judges | At most 1 MiB. A larger playbook is refused before `mmx explain` runs | [Triage agent](triage-agent.md#reading-a-playbooks-node-tasks): MMHotline reads the whole playbook into memory. The largest playbook in a reference four-server setup is 68 KiB, so 1 MiB is about 15 times that. The agent can split a larger playbook. |
| The inventories' servers for the triage agent | At each run's start, MMHotline lists the inventory servers again and permits proxy connections to each server's name at port 22. A failed listing leaves the run going without access to the unlisted servers | [Triage agent](triage-agent.md#reading-the-servers-over-ssh): the agent reads servers over SSH and nothing else. Server destinations follow the inventory, which only a person changes. A missing listing must not stop a run. |
| The vendor pages' hosts for the triage agent | The host of each `https://` `releases_page` and `security_advisories_page` in `software_outside_the_distribution.yml`, at port 443 or the port the address names. At each run's start, MMHotline lists the hosts again from MMHotline's systems repository copy at the commit used to start the agent's copy. A page MMHotline cannot list is left out with the reason, and the run continues | [Triage agent](triage-agent.md#the-vendor-pages-hosts): the software review reads the release and security advisory pages. Manual listing would duplicate hosts in `software_outside_the_distribution.yml` and `triage_agent.listed_hosts`. The proxy would refuse access to a newly added program's vendor host until someone listed the host. The proxy carries HTTPS only. |
| Hosts listed from the systems repository, for runs outside it | A setup test, a sign-in check, and a review of a proposed playbook reach neither inventory servers nor vendor page hosts | [Triage agent](triage-agent.md#internet-access): only a run in the systems repository has the repository the hosts come from. |
| MMX run time limit | One hour, the wait for another run included | [Triage agent](triage-agent.md#the-time-limit): a fix for an incident takes minutes; a hung run must not hold MMHotline's MMX runs forever. |
| The run request's server list | `inventory_servers` may be at most 16 MiB as JSON, apart from the run socket's 1 MiB line | [Triage agent](triage-agent.md#the-run-socket): at about 100 bytes a server, the 1 MiB stopped runs near 8,000 servers, and 16 MiB lists about 160,000, far beyond the fleets MMHotline serves. The sandbox reads the request line whole into memory, so the list still needs a bound. |
| A finished run's commits when MMHotline stops | Saved first as `triage_agent_returned_commits/RUN_ID_BASE.bundle` in the state directory; MMHotline's stop ends the wait for the copy's lock, and the next run in the systems repository after the restart pushes them first | [Triage agent](triage-agent.md#a-finished-runs-commits-and-mmhotlines-stop): a stop must never wait for an MMX run that holds the lock, and must never lose the agent's commits. A file holds a bundle of up to 64 MiB only until the next run; serve's start must not wait for the lock. |
| Lock holder line on the triage session page | At most 300 characters | [Triage agent](triage-agent.md#waiting-for-the-copys-lock): other users' helpers write the line, and one line names a holder in far fewer characters. |
| Waiting marker beside the copy's lock | `systems_repository.lock.waiting`, mode 0644, rewritten each second while MMHotline waits | [Triage agent](triage-agent.md#waiting-for-another-run): a long holder such as a restore drill sees the wait and gives way, because the wait counts toward the MMX run time limit; the line holds no secret. |
| Alerts that start a triage session | Warning (`warn`) and SOS (`sos`) from alert sources and people. MMHotline's own SOS about a source that stopped checking in or whose SOS alerts MMHotline refused also counts. MMHotline's notices about MMHotline's own work and the agent's reports never count | [Triage agent](triage-agent.md#what-starts-or-joins-a-session): the qualifying alerts concern the team's servers. Sending the agent's own reports back to the agent would repeat the agent's words. |
| Where the triage agent learns the task forms of each kind of action | About 5,000 characters of forms appear in the task prompt of a session's first run and in the prompt of a software review. MMHotline generates the forms from the table used to judge playbook tasks. No command supplies the forms | [Triage agent](triage-agent.md#the-task-prompt): receiving accepted task forms before writing a playbook helps the agent write tasks MMHotline can classify at once. A command helps only an agent that knows to run the command. |
| Triage session prompt | At most 64 KiB in JSON. Each alert's message is cut at 2,000 characters. When whole alerts do not fit, the alert list ends with "And N more alerts" | [Triage agent](triage-agent.md#the-task-prompt): the coding agent reads the whole prompt into its context, and one long message must not push the other alerts out. |
| Notes from the team in a triage prompt | Each note goes once to the next run of the note's incident's session, whatever the run carries. If no further run starts, the note waits for a later session's first run with the incident or an alert of the incident's cause. Notes use at most a quarter of the prompt's 64 KiB. When more notes wait, the prompt keeps the newest notes, followed by "And N older notes" | [Triage agent](triage-agent.md#notes-from-the-team): a session covers all incidents in the session, and the agent retains received notes in the agent's session. A note about a cause helps the next session investigating the cause. The alerts, which are the evidence, always keep room. |
| A triage run cut short by MMHotline's stop or restart | Resumed with the alerts and the notes from the team carried by the interrupted run | [Triage agent](triage-agent.md#after-a-restart): the agent keeps its session files, so the agent continues with the saved context instead of the session waiting for the next alert. |
| Time an SOS waits for the triage agent | The settings file's `triage_agent.sos_waits_for_the_agent_minutes`, a whole number from 0 to 15; 3 is a good start. 0 wakes the person on call at once while the agent still looks. Before the settings file applies a value, 3 minutes. Only the first waking step waits | [Triage agent](triage-agent.md#an-sos-waits-for-the-agent): the wait gives the agent a chance to fix the problem before anyone is woken. Teams weigh that differently: a team with customers on a service-level agreement may want 0, and a team of one may let the agent try first. 3 minutes covers one routine fix and its confirmation: in measured runs on 2026-11-11 the agent's fix was done 55 seconds after the session started, the alert resolved about 2 minutes later, and a hand-over came 1:00 to 1:50 after the start. A stuck or wrong agent must not hold an SOS longer than 15 minutes. |
| Time a warn waits for the triage agent | The settings file's `triage_agent.warn_waits_for_the_agent_minutes`, a whole number from 0 to 30; it may be left out, which is 15. 0 holds nothing. Every warn from an alert source that starts or joins a triage session is held, with one set of rules | [Triage agent](triage-agent.md#a-warn-waits-for-the-agent): nothing reaches a person before the agent has looked. 15 covers a run of 30 to 70 seconds plus a wait behind another run, a software review that makes way, or an MMX run that holds the systems repository; a warn is not urgent. The maximum is 30 because a warning held longer than half an hour no longer gives a person the news in time to plan the day's work. |
| Alerts a report or playbook run request covers | The alerts it names with `--about-alert-id`; with the option left out, the one alert its run carried, or none when the run carried several | [Triage agent](triage-agent.md#reports-and-requests-name-their-alerts): one verdict must not quiet another finding. One problem is not enough, as two warns can share one `sender_incident_key`. |
| Alerts one run carries | The alerts its 64 KiB prompt shows; at least one waiting alert, its message cut to fit | [Triage agent](triage-agent.md#the-task-prompt): a report must not cover a warning the agent never saw, and a run that carries nothing would be followed by the same prompt. |
| Held alerts queued per background visit | At most 100, each in its own transaction | [Triage agent](triage-agent.md#a-warn-waits-for-the-agent): a take-over of a session with thousands of held warns must not hold up the visit's other work; a visit that queued some brings the next at once. |
| Longer wait of an SOS while the triage agent replaces a server | The settings file's `triage_agent.sos_waits_for_a_server_replacement_minutes`, a whole number from 0 to 60, counted from the replacement's start; 10 is a good start and the value before the settings file applies one. 0 turns it off. One warn alert at the start; a failed run of the replacement wakes the person at once | [Triage agent](triage-agent.md#an-sos-waits-for-a-server-replacement): a measured replacement by the agent alone took about 5 to 6 minutes, and 10 adds a margin; a later measurement may change it. One MMX run may take up to an hour, so a longer wait would hold an SOS for a replacement MMHotline would already have ended. |
| An SOS a person creates by hand during a triage session | Never waits for the triage agent. The manually created SOS still joins the session | [Triage agent](triage-agent.md#an-sos-waits-for-the-agent): a person who creates an SOS wants someone now. |
| Time `incidents send-test-sos` waits for a claim | `--wait-for-claim-minutes`, at least 1, default 10 | [Incidents](incidents.md#the-test-sos): a whole step of the default time to claim (5 minutes) plus the start of the backup's step; a phone silent by then has a setup problem. |
| Test SOS and the triage agent | The test never waits for the agent and starts no session | [Incidents](incidents.md#the-test-sos): nothing is wrong, so the agent has nothing to look into, and the test must wake the person at once. |
| Test SOS for one person (`--sign-in-email-address`) | Goes to that person only, with no time to claim, backup step, or escalation | [Incidents](incidents.md#the-test-sos): a new team member who is not on call proves their own phone, and the test must not wake anyone else. |
| Test SOS without `--sign-in-email-address` in a team of one | Goes to that one person, as with the flag | [Incidents](incidents.md#the-test-sos): a first install has one person, so the short command does the only test there is. |
| Triage session start message | Off: the settings file's `triage_agent.send_a_message_when_the_agent_starts_looking` may be left out, which is `false`. With `true`, one info message per session to the person on call, and none when nobody is available | [Triage agent](triage-agent.md#the-start-message): the message is an ordinary info alert, which Pushover delivers, so it reached phones before the agent had looked; the dashboard and the session's page show the agent at work. A quiet message is no reason to reach an unavailable person. |
| An SOS's email and chat while it waits for the agent | They wait with the first waking step, and go when the wait is over; sent to nobody when the SOS resolves during the wait with nobody claiming it | [Triage agent](triage-agent.md#an-sos-waits-for-the-agent): nothing reaches a person before the agent has looked, and queued apart from the wake, the alert source's share of SOS deliveries can never undo a wake. |
| Software review interval | Off: no scheduled software review until the settings file sets `triage_agent.software_review_interval_hours`, a required key, to a whole number of hours from 1 to 8,760 instead of `off`. The software review guide's example writes `off` and suggests 24 hours for a team that turns the review on. The first review starts right after the interval first applies, when none has run | [Triage agent](triage-agent.md#the-software-review-interval): each review is a paid run of the coding agent, and the team should choose that cost rather than be surprised by it on a bill; `run-software-review` measures one review's cost first. A review runs up to an hour, so a shorter interval would only run reviews back to back; the deadline arithmetic needs a bound, and more than 365 days is far beyond any use. |
| The software review's task | The team's `scheduled_software_review_task.md` at the top of the systems repository, read from MMHotline's copy at the review's starting commit, at most 64 KiB. A missing, empty, or larger file fails the review before it starts, with a reason that says what to do; the failed review counts | [Triage agent](triage-agent.md#the-software-reviews-task): the team knows which software it runs; MMHotline keeps only the frame it owns. Only a person's commits change the file, so the agent cannot rewrite its own task. 64 KiB is a session prompt's bound: the whole prompt goes into the coding agent's context. A failure that did not count would repeat every second. |
| A software review and a triage session | A due software review waits while a triage run is active. Whatever would start a session's run stops a running software review after the agent's current step | [Triage agent](triage-agent.md#when-a-software-review-starts): incidents come first. A software review can run an hour, and an SOS waits only 5 minutes for the agent. A session waiting for a person, such as for approval, needs no run and would otherwise delay software reviews for days. |
| A software review that does not finish | A failed software review counts for scheduling. A software review interrupted by MMHotline stopping, restarting, or needing the agent for a triage session starts again | [Triage agent](triage-agent.md#when-a-software-review-starts): starting again after a failure would repeat the failure every second. Interruption by MMHotline stopping, restarting, or starting a session's run must not skip a whole review interval. |
| Review time limit | 10 minutes for each review of a proposed playbook. After a timeout, a person decides whether to approve the playbook run | [Triage agent](triage-agent.md#how-a-review-runs): the review agent reads one playbook and answers in a minute or two. The triage run waits for the review, so a stuck review agent must not delay the triage run indefinitely. |
| Review prompt | At most 256 KiB in JSON, including the triage agent's diagnosis and the review agent's earlier refusal reasons for the problem. A longer prompt is not cut, and a person decides | [Triage agent](triage-agent.md#the-review-prompt): the review agent reads the whole prompt into its context, and a review of a cut playbook would approve text the review agent never saw. |
| Review agent refusals before a person decides | 3 in a row on one problem, a constant rather than a setting. The first two refusals go back to the triage agent | [Triage agent](triage-agent.md#refusal-rounds): each round is a paid run of the triage agent and review agent while the outage continues. More than three refusals usually means the triage agent and review agent disagree about the problem, so a person must decide. |
| The triage agent's diagnosis | Required with each request to execute a playbook in an inventory. The diagnosis is Markdown, at most 64 KiB, as a report | [Triage agent](triage-agent.md#requests-from-the-agent): the review agent and approving person judge the playbook against the triage agent's findings. A person reads the diagnosis. One run socket line carries the diagnosis. |
| What a review reaches | Only the review agent's own coding agent service, whatever the triage agent's internet access | [Triage agent](triage-agent.md#how-a-review-runs): a review needs only its prompt and its model. A review agent misled by the playbook's text must reach nothing else. |
| A Claude Code subscription token's expiry | 365 days after the settings file's credential applied; a change of only the model or reasoning effort keeps the date; a reminder to administrators 30 days and 7 days before, each once, and a new credential starts the 30-day and 7-day reminders again | [Triage agent](triage-agent.md#expiry-reminders): following the guide to keeping the agents signed in, a person runs `claude setup-token` just before adding the token to the settings file. The token is valid for one year. A 30-day reminder leaves time to reach the team's Claude account holder. The 7-day reminder is the last call. |
| A Codex access token's expiry | The start of the settings file's `credential_expires_on`, in UTC; the same 30-day and 7-day reminders; a token that applies with 30 days or less left gets only the 7-day reminder | [Triage agent](triage-agent.md#expiry-reminders): MMHotline cannot read the end date from the token. The token may stop at any time on its last day. A reminder at the moment the person made a short token would tell them nothing new. |
| How often a run reads a ChatGPT sign-in's `auth.json` while Codex runs | Once a second, and once more after Codex exits | [Triage agent](triage-agent.md#codex-with-a-chatgpt-sign-in): a run killed during a refresh loses at most about a second of a refresh token that works only once. Reading a small file once a second costs nothing. |
| Largest ChatGPT sign-in | 64 KiB, in the settings file and in each copy a run sends back | [Triage agent](triage-agent.md#codex-with-a-chatgpt-sign-in): real `auth.json` files are a few KiB; 64 KiB keeps one credential far below the run socket's 1 MiB line. |
| Sign-in check | Once a day for each agent, unless a run of that agent succeeded in the last 24 hours. | Sign-in alerts | One warn alert when a check fails and one info alert when a run of the agent succeeds again, to administrators only | [Triage agent](triage-agent.md#the-daily-sign-in-check): no repeats while the check keeps failing; only an administrator can set up a new credential. |

| How MMHotline asks for an approval | An alert at sos joins an open incident associated with the asking run's alerts, otherwise a claimed incident, otherwise a new incident. | Approval and warning notification text | The first diagnosis paragraph, as plain text cut at a word to 300 characters. Review text is cut at a word to 300 characters | [Triage agent](triage-agent.md#asking-for-approval): a person can decide from a short reason and the cause for permission. The approval request's or warned run's card keeps the evidence and task details. |

A covered run that failed, could not run, or went stale still used its cover | [Triage agent](triage-agent.md#one-approval-for-a-known-sequence): a woken person approves a known sequence, such as replacing a failed server, once. One session, one use each, and listed playbooks only keep the approval to what the person saw. MMHotline cannot tell whether a failed run changed the servers, so running it again needs a person. |
| Who approves or refuses | Any signed-in team member; 2 approvals come from two different people; one refusal ends the request. A team may remove a person it no longer trusts, so two approvals always come from two current members. |
| Refusal reason | Required, at most 500 characters | [Triage agent](triage-agent.md#approving-or-refusing): a short reason for the agent and the history, not a report. |

| Commit review and the next run | Any signed-in member reviews on Approvals, or root with `commit-reviews mark-reviewed`; one review per commit ID; one alert per commit, and a resolution when MMHotline's warning went out; request the playbook run again | [Triage agent](triage-agent.md#reviewing-a-commit-that-waits): reuse the team's approval workflow and avoid replaying a fix after the surrounding situation changed. |
| Who approves a commit no trusted key signed | Required `systems_repository_commits.commits_without_a_trusted_signature_are_approved_by`: `a_person` or `a_person_or_the_triage_agent`, which the Stack's template sets; only a person before the key applies | [Triage agent](triage-agent.md#the-triage-agent-reviews-a-commit-no-trusted-key-signed): most such commits are a teammate's merge button, and MMX should not stop for hours over one. |
| The triage agent's key without `systems_repository_commits` | `triage_agent.commit_signing_public_key` is allowed and unused; nothing is trusted | [Triage agent](triage-agent.md#checking-commits-before-mmx-and-triage-agent-runs): a lock-out removes one section only, and a refusal there would stop the lock-out's settings from applying. |
| Paths only a person may approve | Required `systems_repository_commits.paths_only_a_person_may_approve`, a short list the Stack fills; MMHotline names no file | [Triage agent](triage-agent.md#the-triage-agent-reviews-a-commit-no-trusted-key-signed): an approved commit must never widen what the triage agent may do or add a key MMHotline trusts; a longer list returns ordinary work to a person. |
| A commit's diff in the commit review's prompt | Cut at 16 KiB in JSON with how many lines are left out; message at 2,000 characters, paths at 4 KiB; the whole prompt within 64 KiB, commits that do not fit left for the next run | [Triage agent](triage-agent.md#the-commit-reviews-prompt): about 400 lines shows an ordinary change whole, and three such commits fit beside the frame; the agent decides `needs_a_person` when a part it cannot see could matter. |
| When the commit review cannot happen | MMHotline's own warning, once, with the reason: a failed run, a run without a decision on the commit, no setup or sandbox, or a setting that no longer lets the agent approve | [Triage agent](triage-agent.md#one-alert-per-commit): no commit may wait with nobody told, and each commit gets one alert, also across a restart. |
| What a triage run keeps in the agent's home | Clear everything except `.ssh/`, `.gitconfig`, `.claude/projects/`, and `.codex/sessions/` at each run's start | [Triage agent](triage-agent.md#what-a-run-leaves-for-the-next): a newer coding agent can read settings from a new place, and a list of known files would miss it without anyone noticing. |
| Supported coding agent versions | Codex 0.166.0 or newer, Claude Code 2.1.325 or newer; the team moves the version | [Triage agent](triage-agent.md#supported-coding-agent-versions): a team should get a new model without waiting for an MMHotline release, and every change MMHotline relies on fails a run visibly. |
| Commits the triage agent approved on Approvals | The latest 50, newest first | [Triage agent](triage-agent.md#what-people-see): the page stays short; `commit-reviews show` reads any commit by its ID. |

Keep values as named constants unless the existing design requires a team
setting. A future adjustment is an ordinary code, test, and specification
change, not a reason to build a settings framework now.
